# Continuación del BD contexto.md - Extensiones para la Base de Datos JORSEGTEC en Supabase

Este archivo es una continuación directa de `BD contexto.md`.

El objetivo de este documento es agregar nuevas tablas a la base de datos simplificada de JORSEGTEC sin romper la estructura ya definida anteriormente.

Las tablas que se desean agregar son:

1. `permiso`
2. `rol_permiso`
3. `estado_proyecto`
4. `bitacora`


IMPORTANTE:

- No se debe eliminar la tabla `rol`.
- No se debe eliminar la tabla `usuario`.
- No se debe eliminar la tabla `proyecto`.
- No se debe eliminar la tabla `bitacora_proyecto`, porque esa tabla cumple otra función.
- La nueva tabla `bitacora` será una bitácora general del sistema.
- La tabla `bitacora_proyecto` seguirá siendo usada para observaciones o avances específicos de un proyecto.
- La tabla `bitacora` será usada para registrar modificaciones realizadas en cualquier parte del sistema.

---

# 1. Motivo de la ampliación

La base de datos simplificada ya permite gestionar usuarios, roles, clientes, empleados, proyectos, órdenes de trabajo, mantenimientos, pagos, gastos, catálogo de productos, cotizaciones, evidencias y archivos.

Sin embargo, para mejorar el control del sistema se agregarán tres mejoras importantes:

## 1.1 Control de permisos por rol

En la versión simplificada, los permisos se manejaban directamente por el rol del usuario desde el código del sistema.

Ahora se desea agregar una estructura más flexible mediante las tablas:

- `permiso`
- `rol_permiso`

Esto permitirá definir qué acciones puede realizar cada rol.

Ejemplo:

- El Administrador puede crear, editar, eliminar y ver todo.
- El Técnico Superior puede crear órdenes y asignar técnicos.
- El Técnico de Campo puede ver sus órdenes y subir evidencias.
- Atención al Cliente puede registrar clientes y consultar estados.

---

## 1.2 Estados de proyecto normalizados

En la base simplificada, el estado del proyecto estaba como un campo tipo `ENUM` dentro de la tabla `proyecto`.

Ejemplo anterior:

```text
proyecto.estado
```

Ahora se quiere agregar una tabla independiente:

```text
estado_proyecto
```

Esto permite que los estados estén mejor organizados y sean más fáciles de administrar.

---

## 1.3 Bitácora general del sistema

Se agregará una tabla llamada:

```text
bitacora
```

La nueva bitácora solamente debe guardar información sobre modificaciones realizadas en el sistema.

Debe registrar:

- usuario que modificó,
- fecha,
- hora,
- qué dato o información se modificó,
- estado anterior,
- estado actual,
- dirección IP desde donde se realizó la modificación.

---

# 2. Tablas nuevas que se agregarán

---

# 2.1 Tabla: `permiso`

La tabla `permiso` almacena las acciones o permisos disponibles dentro del sistema.

Esta tabla sirve para controlar qué puede hacer cada rol.

## Estructura de la tabla

| Atributo | Tipo sugerido en Supabase/PostgreSQL | Descripción |
|---|---|---|
| `id_permiso` | BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY | Identificador único del permiso |
| `nombre_permiso` | VARCHAR(100) NOT NULL | Nombre del permiso |
| `codigo_permiso` | VARCHAR(100) NOT NULL UNIQUE | Código interno del permiso |
| `modulo` | VARCHAR(100) NOT NULL | Módulo al que pertenece el permiso |
| `descripcion` | TEXT | Descripción del permiso |
| `estado` | BOOLEAN DEFAULT TRUE | Indica si el permiso está activo |
| `fecha_creacion` | TIMESTAMP DEFAULT NOW() | Fecha de creación del permiso |

## Campos obligatorios

Los campos obligatorios son:

- `nombre_permiso`
- `codigo_permiso`
- `modulo`

## Ejemplos de permisos

| Módulo | Nombre del permiso | Código sugerido |
|---|---|---|
| Clientes | Crear cliente | `crear_cliente` |
| Clientes | Editar cliente | `editar_cliente` |
| Clientes | Ver cliente | `ver_cliente` |
| Empleados | Crear empleado | `crear_empleado` |
| Proyectos | Crear proyecto | `crear_proyecto` |
| Proyectos | Editar proyecto | `editar_proyecto` |
| Proyectos | Cambiar estado de proyecto | `cambiar_estado_proyecto` |
| Órdenes de trabajo | Crear orden | `crear_orden` |
| Órdenes de trabajo | Asignar técnico | `asignar_tecnico` |
| Órdenes de trabajo | Finalizar orden | `finalizar_orden` |
| Evidencias | Subir evidencia | `subir_evidencia` |
| Mantenimientos | Programar mantenimiento | `programar_mantenimiento` |
| Mantenimientos | Reprogramar mantenimiento | `reprogramar_mantenimiento` |
| Finanzas | Registrar pago | `registrar_pago` |
| Finanzas | Registrar gasto | `registrar_gasto` |
| Catálogo | Crear producto | `crear_producto` |
| Cotizaciones | Crear cotización | `crear_cotizacion` |
| Cotizaciones | Exportar PDF | `exportar_cotizacion_pdf` |
| Reportes | Ver reportes | `ver_reportes` |

## Relación

La tabla `permiso` se relaciona con la tabla `rol` mediante la tabla intermedia `rol_permiso`.

Cardinalidad:

```text
rol *..* permiso
```

Como una relación muchos a muchos no se implementa directamente en una base relacional, se crea la tabla intermedia:

```text
rol_permiso
```

# 2.2 Tabla: `rol_permiso`

La tabla `rol_permiso` relaciona los roles con los permisos.

Sirve para indicar qué permisos tiene cada rol del sistema.

## Estructura de la tabla

| Atributo | Tipo sugerido en Supabase/PostgreSQL | Descripción |
|---|---|---|
| `id_rol_permiso` | BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY | Identificador único |
| `id_rol` | BIGINT NOT NULL | Rol relacionado |
| `id_permiso` | BIGINT NOT NULL | Permiso relacionado |
| `fecha_asignacion` | TIMESTAMP DEFAULT NOW() | Fecha en que se asignó el permiso |
| `estado` | BOOLEAN DEFAULT TRUE | Indica si la relación está activa |

## Llaves foráneas

```text
id_rol     → rol.id_rol
id_permiso → permiso.id_permiso
```

## Restricción recomendada

Para evitar que el mismo permiso se asigne dos veces al mismo rol, se recomienda agregar una restricción única:

```text
UNIQUE(id_rol, id_permiso)
```

## Relación

```text
rol 1..* rol_permiso
permiso 1..* rol_permiso
```

Interpretación:

- Un rol puede tener muchos permisos.
- Un permiso puede estar asignado a muchos roles.
- La tabla `rol_permiso` permite manejar esta relación muchos a muchos.

---

# 2.3 Tabla: `estado_proyecto`

La tabla `estado_proyecto` almacena los estados permitidos para los proyectos.

Antes, en la base simplificada, el estado estaba dentro de la tabla `proyecto` como un campo `ENUM`.

Ahora, para mejorar la escalabilidad, se usará una tabla independiente.

## Estructura de la tabla

| Atributo | Tipo sugerido en Supabase/PostgreSQL | Descripción |
|---|---|---|
| `id_estado_proyecto` | BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY | Identificador del estado |
| `nombre_estado` | VARCHAR(50) NOT NULL | Nombre del estado |
| `descripcion` | TEXT | Descripción del estado |
| `orden_estado` | INT NOT NULL | Orden secuencial del estado |
| `estado` | BOOLEAN DEFAULT TRUE | Indica si el estado está activo |

## Estados recomendados

Los estados recomendados para proyectos son:

| Orden | Estado |
|---|---|
| 1 | Registrado |
| 2 | Cotizado |
| 3 | Aprobado |
| 4 | En ejecución |
| 5 | Finalizado |
| 6 | Cancelado |

## Relación con `proyecto`

Se debe agregar un nuevo campo en la tabla `proyecto`:

```text
id_estado_proyecto
```

Este campo será una llave foránea hacia:

```text
estado_proyecto.id_estado_proyecto
```

## Relación

```text
estado_proyecto 1..* proyecto
```

Interpretación:

- Un estado puede estar asignado a muchos proyectos.
- Un proyecto tiene un solo estado actual.

---

# 2.4 Tabla: `bitacora`

La tabla `bitacora` será una bitácora general del sistema.

Esta tabla reemplaza a la tabla o idea anterior llamada:

```text
actividad_sistema
```


## Importante

No confundir:

```text
bitacora
```

con:

```text
bitacora_proyecto
```

Son tablas diferentes.

## Diferencia entre ambas tablas

| Tabla | Función |
|---|---|
| `bitacora` | Guarda modificaciones generales realizadas en el sistema |
| `bitacora_proyecto` | Guarda observaciones, avances o comentarios específicos de un proyecto |

## Estructura de la tabla `bitacora`

| Atributo | Tipo sugerido en Supabase/PostgreSQL | Descripción |
|---|---|---|
| `id_bitacora` | BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY | Identificador de la bitácora |
| `id_usuario` | BIGINT NOT NULL | Usuario que realizó la modificación |
| `tabla_modificada` | VARCHAR(100) NOT NULL | Nombre de la tabla modificada |
| `id_registro_modificado` | BIGINT | ID del registro modificado |
| `campo_modificado` | VARCHAR(100) | Campo específico que fue modificado |
| `accion` | VARCHAR(50) NOT NULL | Acción realizada: INSERT, UPDATE, DELETE |
| `valor_anterior` | TEXT | Valor anterior antes del cambio |
| `valor_actual` | TEXT | Valor nuevo después del cambio |
| `descripcion_cambio` | TEXT NOT NULL | Explicación clara de lo que se modificó |
| `ip_usuario` | INET | Dirección IP del usuario |
| `fecha_modificacion` | DATE DEFAULT CURRENT_DATE | Fecha de modificación |
| `hora_modificacion` | TIME DEFAULT CURRENT_TIME | Hora de modificación |
| `fecha_hora_modificacion` | TIMESTAMP DEFAULT NOW() | Fecha y hora completa del cambio |

## Llave foránea

```text
id_usuario → usuario.id_usuario
```

## Relación

```text
usuario 1..* bitacora
```

Interpretación:

- Un usuario puede generar muchos registros de bitácora.
- Cada registro de bitácora pertenece a un usuario.

## Qué debe registrar esta tabla

La tabla `bitacora` debe registrar modificaciones importantes, por ejemplo:

- cambio de estado de un proyecto,
- edición de datos de un cliente,
- edición de datos de un empleado,
- modificación de una orden de trabajo,
- cambio de fecha de mantenimiento,
- cambio de precio de un producto,
- modificación de una cotización,
- registro o edición de pagos,
- registro o edición de gastos.

## Ejemplo conceptual

Si un usuario cambia el estado de un proyecto de `Cotizado` a `Aprobado`, la bitácora debería guardar:

| Campo | Ejemplo |
|---|---|
| `id_usuario` | 3 |
| `tabla_modificada` | proyecto |
| `id_registro_modificado` | 15 |
| `campo_modificado` | id_estado_proyecto |
| `accion` | UPDATE |
| `valor_anterior` | Cotizado |
| `valor_actual` | Aprobado |
| `descripcion_cambio` | El usuario cambió el estado del proyecto de Cotizado a Aprobado |
| `ip_usuario` | 192.168.1.20 |
| `fecha_modificacion` | 2026-05-15 |
| `hora_modificacion` | 18:30:00 |

# 3. Cambios necesarios en tablas existentes

---

# 3.1 Cambios en la tabla `proyecto`

La tabla `proyecto` ya existía en la base de datos simplificada.

Antes tenía este campo:

```text
estado : ENUM
```

Ahora se agregará este campo:

```text
id_estado_proyecto : BIGINT
```

Este nuevo campo se relaciona con la tabla:

```text
estado_proyecto
```

## Estructura actualizada de `proyecto`

La tabla `proyecto` debe quedar así:

| Atributo | Tipo sugerido | Descripción |
|---|---|---|
| `id_proyecto` | BIGINT PRIMARY KEY | Identificador |
| `id_cliente` | BIGINT FK | Cliente |
| `id_ubicacion` | BIGINT FK | Ubicación del servicio |
| `id_tipo_servicio` | BIGINT FK | Tipo de servicio |
| `id_estado_proyecto` | BIGINT FK | Estado actual del proyecto |
| `codigo_proyecto` | VARCHAR(50) | Código interno |
| `nombre_proyecto` | VARCHAR(150) | Nombre del proyecto |
| `descripcion` | TEXT | Descripción |
| `monto_cotizado` | NUMERIC(10,2) | Monto cotizado |
| `fecha_inicio_estimada` | DATE | Fecha estimada de inicio |
| `fecha_fin_estimada` | DATE | Fecha estimada de finalización |
| `fecha_inicio_real` | DATE | Fecha real de inicio |
| `fecha_fin_real` | DATE | Fecha real de finalización |
| `fecha_registro` | TIMESTAMP | Fecha de registro |
| `id_usuario_registro` | BIGINT FK | Usuario que registró |

## Recomendación de migración sin romper la base

Para no romper lo ya hecho, se recomienda hacer la migración en fases:

### Fase 1

Crear la tabla `estado_proyecto`.

### Fase 2

Insertar los estados base:

```text
Registrado
Cotizado
Aprobado
En ejecución
Finalizado
Cancelado
```

### Fase 3

Agregar el campo `id_estado_proyecto` a la tabla `proyecto`.

### Fase 4

Actualizar los proyectos existentes asignando el estado correspondiente.

### Fase 5

Cuando todo funcione correctamente, se puede dejar de usar el campo antiguo:

```text
estado
```

### Fase 6 opcional

Eliminar el campo antiguo `estado`, solamente si ya no se usa en el sistema.

## Importante

Si la aplicación ya está usando el campo `estado` en el frontend o backend, no debe eliminarse inmediatamente.

Primero se debe modificar el código para usar:

```text
id_estado_proyecto
```

Después recién se puede eliminar el campo antiguo.

# 4. Relaciones nuevas agregadas

## 4.1 Relación entre `rol`, `permiso` y `rol_permiso`

```text
rol 1..* rol_permiso
permiso 1..* rol_permiso
```

Equivale a:

```text
rol *..* permiso
```

Interpretación:

- Un rol puede tener varios permisos.
- Un permiso puede estar en varios roles.

---

## 4.2 Relación entre `estado_proyecto` y `proyecto`

```text
estado_proyecto 1..* proyecto
```

Interpretación:

- Un estado puede estar asignado a muchos proyectos.
- Un proyecto tiene un solo estado actual.

---

## 4.3 Relación entre `usuario` y `bitacora`

```text
usuario 1..* bitacora
```

Interpretación:

- Un usuario puede realizar muchas modificaciones.
- Cada modificación registrada en la bitácora pertenece a un usuario.

---

# 5. Cardinalidades actualizadas

Estas son las nuevas cardinalidades que deben agregarse al documento principal.

| Relación | Cardinalidad | Descripción |
|---|---|---|
| `rol` — `rol_permiso` | 1..* | Un rol puede tener muchos permisos asignados |
| `permiso` — `rol_permiso` | 1..* | Un permiso puede estar asignado a muchos roles |
| `rol` — `permiso` | *..* | Relación muchos a muchos mediante `rol_permiso` |
| `estado_proyecto` — `proyecto` | 1..* | Un estado puede pertenecer a muchos proyectos |
| `usuario` — `bitacora` | 1..* | Un usuario puede generar muchos registros de bitácora |

# 6. Módulos afectados por estas nuevas tablas

---

# 6.1 Módulo de autenticación y control de acceso

Tablas existentes:

- `rol`
- `usuario`
- `empleado`

Tablas nuevas:

- `permiso`
- `rol_permiso`

Con estas tablas, el módulo de autenticación y control de acceso queda más completo.

Ahora no solo se controla el acceso por rol, sino también por permisos específicos.

Ejemplo:

Un usuario con rol `Técnico de Campo` puede tener permisos como:

- ver sus órdenes asignadas,
- actualizar estado de orden,
- subir evidencia,
- registrar materiales usados.

Pero no debería tener permisos como:

- registrar pagos,
- eliminar usuarios,
- modificar precios,
- ver reportes financieros.

---

# 6.2 Módulo de gestión de proyectos

Tabla existente:

- `proyecto`

Tabla nueva:

- `estado_proyecto`

La tabla `estado_proyecto` permite normalizar los estados del proyecto.

Esto mejora la organización y evita errores de escritura.

Ejemplo:

Sin tabla:

```text
En ejecucion
En ejecución
ejecución
En proceso
```

Con tabla:

```text
id_estado_proyecto = 4 → En ejecución
```

---

# 6.3 Módulo de auditoría o bitácora general

Tabla nueva:

- `bitacora`

La tabla `bitacora` registra modificaciones generales del sistema.

Sirve para saber:

- quién modificó,
- cuándo modificó,
- qué modificó,
- qué valor tenía antes,
- qué valor tiene ahora,
- desde qué IP se realizó el cambio.

Esto ayuda a tener control, trazabilidad y seguridad.

---

# 7. Reglas importantes para la IA o desarrollador que implemente esto

Estas reglas son obligatorias para no modificar mal la base de datos.

## Regla 1

No eliminar la tabla `rol`.

La tabla `rol` seguirá siendo la base de los roles del sistema.

---

## Regla 2

No eliminar la tabla `usuario`.

La tabla `usuario` seguirá conectada con:

```text
empleado
rol
bitacora
```

---

## Regla 3

No eliminar la tabla `bitacora_proyecto`.

La tabla `bitacora_proyecto` no es lo mismo que `bitacora`.

Debe mantenerse porque guarda comentarios, avances y observaciones de proyectos.

---

## Regla 5

La tabla `estado_proyecto` reemplaza progresivamente el campo `estado` de `proyecto`.

No se debe eliminar el campo `estado` de forma inmediata si el sistema todavía lo usa.

Primero se debe migrar la información y actualizar el código.

---

## Regla 6

La tabla `permiso` no se conecta directamente con `usuario`.

La conexión correcta es:

```text
usuario → rol → rol_permiso → permiso
```

---

## Regla 7

La tabla `bitacora` debe registrar cambios importantes del sistema, no comentarios del proyecto.

Para comentarios o avances del proyecto se usa:

```text
bitacora_proyecto
```

---

# 10. Resumen final para implementación

Con estas nuevas tablas, la base de datos de JORSEGTEC queda más preparada para una versión más profesional.

Las mejoras agregadas son:

1. Permisos avanzados por rol.
2. Estados de proyecto normalizados.
3. Bitácora general del sistema.
4. Registro de usuario que modificó información.
5. Registro de fecha y hora de modificación.
6. Registro de estado anterior y estado actual.
7. Registro de IP del usuario.
8. Mejor escalabilidad para futuras versiones.

Estas tablas no rompen la estructura anterior porque:

- `permiso` y `rol_permiso` se conectan a `rol`.
- `estado_proyecto` se conecta a `proyecto`.
- `bitacora` se conecta a `usuario`.
- No se elimina `bitacora_proyecto`.
- No se elimina `rol`.
- No se elimina `usuario`.
- No se elimina `proyecto`.
- No se modifica el acceso del cliente, porque el cliente sigue sin usuario.
- No se agrega inventario real, porque el sistema sigue trabajando solo con catálogo de productos y precios.
